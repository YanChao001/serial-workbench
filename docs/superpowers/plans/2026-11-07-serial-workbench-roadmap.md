# Serial Workbench M0—M6 推进计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按 247 条追踪记录完成独立 Host、Node 插件与全能力 GUI/CLI/MCP 工作台，并依次完成软件、硬件和发行验收。

**Architecture:** Rust Host 唯一拥有设备、发送仲裁、原始流和任务；桌面、浏览器、CLI、MCP 与 Node 插件使用同一能力目录和状态。先用纵向场景固定基座，在 M3 冻结首版公开契约，再按领域并行扩展内置与市场插件。

**Tech Stack:** Tauri 2、Rust 1.99.1、React 19、TypeScript、pnpm 12.16.1；开发 Node 26.13.0，随包 runtime 在 M0 固定。

**Spec:** [总设计](../specs/2026-11-07-serial-workbench-design.md)、[功能矩阵](../specs/2026-11-07-serial-workbench-feature-matrix.md)。

## Global Constraints

- Windows x64：Windows 10 22H2；Windows 11 24H2/25H2，26H2 进入新增测试清单。
- macOS arm64/x64：macOS 14 作为最低测试边界，两种架构分别构建与运行。
- Linux x64 glibc：Ubuntu 22.04/24.04、Debian 12 作为基础测试目标。
- 原始 RX 保存接收字节；原始 TX 保存全部变换后的字节及后端实际接受范围，部分写入和未知结果分别呈现。
- 所有纳入的业务、设置、工作区和插件管理功能同时提供 GUI/CLI/MCP 路径；AI 功能调用携带 GUI 定位。
- 保留 HashRouter、原生门面、Rust DTO 类型来源、设置 revision/迁移/未来格式保护、中英词典及未保存工作协商。
- 可信 Node 按当前 OS 用户权限执行，普通设备授权与代码执行、插件管理授权分开。
- M0 删除旧插件架构及其 runtime、包、SDK、桥接、构建测试链和失效指南；旧软件 API/数据格式不兼容，合理职责按新合同复用。
- 所有开发分支与 main 均保持线性历史，同步只用 fast-forward 或 rebase，禁止创建 merge commit；从最新 main 使用短名分支，经 PR squash merge 集成，完成后及时删除本地/远端分支与用完的来源分支。
- 日常界面检查使用无头浏览器；真实窗口在独立环境或用户安排的前台时段验收。共享 target 的 Cargo/绑定任务串行。
- 项目自有工程文档、提交主题/正文和 PR 文案使用中文；Conventional Commit 类型/模块、技术标识及第三方许可保留原文，不启用反复生成英文提交的自动入口。
- 按可验收里程碑集中提交，同一切片的实现、测试、审阅修正和配套文档合一，不按测试步骤或一两行修改拆提交。
- 日常本机验证，Actions 保持启用；积累到 M0/M1 等大节点才手动运行完整跨平台 CI，发布与 Pages 的公开操作按各自验收与授权执行。

## Review Focus

- 并发客户端、重连和旧会话代次不能造成重复 TX；M1/M2 验证请求去重、参数冲突、结果过期和未知结果查询。
- GUI 卡顿、慢盘、慢插件和大结果不能堵塞原始采集或停止通道；M1/M3 验证有界队列、缺口及写盘终态。
- 关页面、断客户端、停任务和退出 Host 有不同效果；M1/M2 验证任务负责人、租约与真实收尾。
- 撤权后的结果、快照、事件、错误和文件引用不能继续泄露内容；M2/M3 用相同身份覆盖各返回通道。
- 软件金样通过不能替代目标平台、驱动和物理接线结果；M6 分别记录软件、硬件、发行状态与证据。

## 执行与交付规则

用户在 2026-11-07 要求依现有规划持续实施、按里程碑提交并尽量并行，随后明确清爽重构、不兼容旧软件。总设计作为方向基线；当前先执行 [M0 计划](./2026-11-07-m0-contracts-and-baseline.md) 中的 [干净基座切片](./2026-11-07-m0-clean-foundation.md)。后续计划以已验收接口为输入，补齐文件、接口、测试和提交点，避免提前围绕临时 SDK 铺开功能包。

协调者维护共享入口、Cargo/npm 清单、锁文件、能力目录、生成绑定和持久格式。并行任务约定文件所有权；需要不同分支时使用隔离 worktree。独立调研、测试对端和金样可先并行；实现任务在其消费的接口可用后启动。任务结束依次完成规格核对、代码评审和所需验证，随后提交；集成后只验证受影响行为。

按计划定义的可验收里程碑使用 Conventional Commits 统一提交，过程中的测试、修正和配套文档累积在该交付中。适用检查与审阅通过后推送短期分支，按仓库 PR 模板自审并 squash merge，随后删除已完成分支；从更新后的 `main` 开始下一切片。主库与 `marketplace/` 分别提交和合并，主库只引用已发布到远端的子模块提交。既有未合入的来源提交先备份并迁入里程碑，确认保留后清理来源分支。

需求定义继续由功能矩阵维护。M0 增加按 ID 记录的软件、硬件、发行状态账本，账本引用 PR/Release 证据；完整日志和单次检查结果留在 PR/Release。别名保留自己的追踪行并共享实现证据；排除、后续和不适用项附范围依据，不能计为实现通过。全局能力的分配仍以矩阵为准。

### M1：设备与最小工作区

按以下六个工作域推进，提交与 PR 统一使用 [M1 精确计划](./2026-11-07-m1-host-and-workspace.md) 的 M1a、M1b 两个里程碑边界；各工作域的实现、测试、审阅修正和文档在所属里程碑集中交付：

1. `crates/core/`：提取无 Tauri 依赖的设备/流/TX 模型及 Virtual 后端；固定 epoch、独立 reader、缺口和部分/未知写回执。
2. `crates/host/` 与本地 CLI：每用户配置实例发现、启动锁、当前用户 IPC、握手、能力 handler、operation 查询/取消和退出结算。两个客户端附着同一 Host。
3. 串口后端：目录、身份、能力、配置与实际回读、控制线/BREAK、队列等待/排空/清空、独立超时及重连；OS 串口和 Unix PTY 软件对端验证。
4. Host 录制/回放：原始录制、分卷索引、水位、独立验证、只读回放、验证前缀另存和磁盘故障；任务不依赖窗口。
5. 最小工作区：桌面附着 Host，基本 Text/HEX、增量 UTF-8、行尾预览、收藏/最近、会话和布局持久化、设置同步、任务与错误；路由、命令、词典与绑定一起接线。
6. 标准 SDK 的 MCP STDIO 适配器：复用同一目录和 handler，首批完成设备发现、连接、读写、录制/回放、任务和设置闭环；建立实际 MCP 客户端验收入口。

可并行：核心接口确定后的串口后端与录制服务；前端视图与独立对端；CLI 和 MCP 适配器。Host 状态所有权、类型生成和注册表串行集成。

出口：GUI/CLI/MCP 操作同一会话；视图冻结不阻断采集；同一请求不会重复发送；配置不确定/BREAK 清线失败会阻止 TX；停止和退出能查询真实终态；读回录制与原始字节、回执相符。矩阵 M1 条目逐项核对，跨阶段条目只记录本阶段完成的部分。

### M2：Node、多客户端和 LAN

1. 正式离线包、固定 runtime 路径及完整性验证、插件后台/register-dispose、worker 监督；终端、图表、自动化三个参考包消费公开 API。
2. Web UI 消息桥与 iframe、浏览器同源入口和配对；桌面与浏览器共用会话，视图关闭后任务继续。输入法、键盘、焦点、主题和大数据传递分别验证。
3. 全能力目录、数据授权、MCP 发现/更新/长任务/取消，AI 跟随、并行活动、草稿保留、暂停跟随与人工接管。
4. LAN 双 Host 配对、设备共享、源端命名空间、观察/控制、请求转发、租约、远端任务与文件引用；IPv4/IPv6 软件对端覆盖断连、撤权、重启和重连。
5. 四个目标的最小发行组件离线启动与插件加载，覆盖无用户 Node/npm、包损坏和 Node 故障恢复。

可并行：后台 SDK 稳定后的三个参考插件与 UI 桥；浏览器客户端和 AI 活动界面；LAN 对端/故障注入。配对、授权、目录与 runtime/打包入口由协调者集成。

出口：三类参考包、两个 Host、桌面/浏览器和 MCP 使用同一资源合同；Rust 原始采集在 Node 故障时继续；A Host 失联后的交互租约与 B 已接受独立任务有各自结果。

## 恢复工作入口

每次续作先读本计划、当前阶段计划和状态账本，再核对 `git status`、实际 HEAD、PR 状态与正在运行的自有任务。以已合入的 `main` 和 PR/Release 验证证据决定下一切片；已通过检查只因新改动、失败或明确疑点重跑。遇到契约缺口先补所属文档与调用者，产品范围变更交由用户澄清。
