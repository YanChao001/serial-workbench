# 25. 采用单主分支的 GitHub Flow 与 squash merge

- 状态：已采纳
- 日期：2026-11-06
- 修订：2026-11-07，全部分支线性、里程碑集中提交与停止自动依赖 PR。
- 相关：[Git 协作规范](../conventions/git-workflow.md)

## 背景与取舍

Serial Workbench 由单人维护，当前按一条版本线开发。维护者需要以 PR 保留改动说明和验证证据，并让主分支及全部开发分支历史线性、按里程碑便于查看。

继续 GitFlow 能区分开发与正式发布历史，但需要维护两条基线和回流顺序；单主分支以版本标签标识正式交付，适合当前维护规模。Squash merge 让每个 PR 在主分支对应一个可回滚的逻辑提交，代价是分支内的提交粒度不会保留到主分支，需要控制 PR 范围并写清最终提交说明。

## 决策

采用 GitHub Flow：`main` 是唯一长期分支，所有改动通过短期分支和 PR 合入，统一 squash merge。功能、紧急修复和版本更新采用相同流程，正式交付以 `main` 上的版本标签标识。单人维护保留 PR 自审与适用检查，审批人数为零。

全部分支禁止 merge commit，同步仅用 rebase 或 fast-forward。按完整里程碑集中提交，将实现、测试、审阅修正和配套文档归入同一提交，不按测试步骤或一两行修正拆分提交。提交主题、正文及 PR 说明使用中文，技术类型和标识保留原文；分支采用任务短名，完成验证、PR squash 后删除本地和远端分支。

停止自动创建依赖升级 PR。原生自动依赖提交不能保证中文主题、正文与里程碑粒度，维护者保留手动审计，集中评估并提交需要的升级；不另建机器人或通用语言检查框架。

具体操作和服务端设置只在 Git 协作规范维护。

## 影响与复查

主分支按 PR 保留里程碑边界，开发分支同步也不引入 merge commit。代价是提交前需要收齐验证和配套修改，审阅修正需回填对应里程碑；已推送的独占分支改写必须使用精确 lease，共享分支不改写，`main` 禁止强推。依赖升级由维护者组织并验证，公开发布沿用独立的发布流程。

未来若需要并行维护多个正式版本，或维护者规模使现有自审与检查不足以支撑合并，再评估维护分支和评审规则。
